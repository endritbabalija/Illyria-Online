# Wuxia MMO — Claude Code guide

A mobile-first 3D wuxia MMO-lite, currently being built as a **vertical slice**: 2 characters, levels 1–30, a shared town hub, 2 hunting zones, 1 dungeon, 1 faction war. Unity 6 client (C#), Nakama server (TypeScript runtime) on PostgreSQL.

**`docs/design.md` is the source of truth.** It holds the pillars, locked decisions, game systems, architecture and the build milestones (M0–M9) with their "done when" criteria. Read the relevant section before starting a milestone. If code and the doc disagree, the doc wins — or flag the conflict and ask; don't silently diverge. Names (Nine Peaks, Lantern Ford, …) are placeholders.

## How to run things

### Server (Nakama + Postgres)

```sh
docker compose -f server/docker-compose.yml up -d --build   # build module + start
docker compose -f server/docker-compose.yml logs -f nakama  # look for "wuxia module loaded"
docker compose -f server/docker-compose.yml down            # stop (add -v to wipe the database)
```

- Ports: `7350` HTTP/WebSocket API (clients use this), `7349` gRPC, `7351` developer console (http://127.0.0.1:7351, default login `admin` / `password`), `5432` Postgres.
- Server key is Nakama's default `defaultkey` — local dev only.
- After changing `server/src/**`, re-run the `up -d --build` command; the module is compiled inside the Docker build.
- Type-check locally without Docker: `cd server && npm install && npm run typecheck`.
- Module rules: `tsc` compiles everything into a single `build/index.js` (`outFile`, ES5 target). **No `import`/`export`** — files share one global scope, and Nakama calls the global `InitModule`. Add new files to `files` in `server/tsconfig.json` (and `tsconfig.test.json`) in dependency order: top-level `var`s run at load (e.g. `combat.ts` calls `f32` from `util.ts`). Runtime types come from `nakama-runtime` (heroiclabs/nakama-common), pinned to the tag that matches the Nakama image version — bump both together.
- Nakama JS runtime quirks: RPC and match handlers must be **top-level named functions** (Nakama finds them by name). **Globals are frozen after `InitModule`** and each VM evaluates them separately, so caches are lazy per-VM (`loadGameData`) and nothing global is mutated. **Match state is converted to plain data between calls** (class instances lose their methods), so the zone match's state is a single closure returning the live `ZoneChannel` (a function survives the round trip; each match has its own VM). Match labels are indexed in batches (~1 s), so `zone_join` remembers channels it just opened in `nk.localcache`.
- Game data in the server: the Dockerfile copies `shared/gamedata/*.json` (an extra build context, `additional_contexts: gamedata` in the compose files) to `/nakama/data/modules/gamedata/`; `loadGameData` reads them with `nk.fileRead` and `parseGameData` checks every cross-reference, so a broken JSON stops the server at startup. Rebuild the image after editing the JSON.
- **Tests**: `cd server && npm test` compiles `src/` + `tests/*.test.ts` into `build-test/tests.js` and runs it in Node (no Docker): the rules against the real JSON (mirroring the client's EditMode tests: shapes per form, rounding, statuses, skill state, items, shop, loot odds), and `ZoneSim` scenarios (two players killing the same wolf, aggro and pack assist, death and revive, ledges, leaps, casts and the queue, loot and the ledger, shops, the safe town, saves), and the walkable grid (decoding, A* round a wall, the real Oak Valley export: no wading across the river, the Han→den path crosses the bridge and matches Unity's 386 m to within 6%, moves into the river corrected, monsters pathing round a wall or giving up). `npm test -- <name filter>` runs a subset. **Integration** against a real Nakama, next to the dev stack without touching it: `docker compose -f server/docker-compose.test.yml up -d --build --wait`, `npm --prefix server run test:integration` (two devices log in, create characters, join one Oak Valley channel, see each other, walk to and kill the same wolf, loot, then read back saves and ledger rows), `docker compose -f server/docker-compose.test.yml down`.
- **Characters and saves**: storage collection `characters`, key = character id (one Kreshnik and one Zana's Chosen per account), owner-read, server-write. Every gold/item change is a row in collection `ledger` (owner-read) written in the **same `storageWrite`** as the character, so they commit together. A joined character carries a session lock (`session: {matchId, until}`) taken with a versioned write; another match refuses the character until it's released on leave or runs out (`server.sessionLockSeconds`), and a failed versioned save kicks the player unsaved — so a character can't be live in two places (no duplication). `session.single_socket`/`single_match` are on in `local.yml`.
- **Zone matches** (`match.ts` → `ZoneSim` in `zone.ts`): one match per channel of `dardana` (town, safe, placeholder layout) or `oak_valley`, at `server.tickRate` (10/s). The server runs monster AI (wander, aggro, chase, leash, pack assist; straight lines on the ground plane, no NavMesh), basic attacks and auto-attack on the locked target, skill forms with the cast queue, statuses, Drangue Leap checks against the zone's ledges, death/revive at the zone's respawn point, HP/Spirit regen, personal loot for the top damage dealer with auto-loot, the bag/gear/shop/potion actions, and move validation (speed, slope, no walking up ledges, and on the zone's walkable grid: no walls, river or thin air). Monsters path on that grid (A*, straightened) and stand at its ground height. Message formats: `server/PROTOCOL.md`.

### Client (Unity)

- Editor version: **Unity 6000.3.27f1** (Unity 6.3 LTS), installed at `C:\Program Files\Unity\Hub\Editor\6000.3.27f1`, with Android Build Support. Created from the Universal 3D (URP) template. Open `client/` via Unity Hub.
- Android SDK/NDK/OpenJDK are **not installed yet** (the editor and Android Build Support were installed from Unity's standalone installers, not through Hub). Add them before the first Android build (M1): Hub → Installs → 6000.3.27f1 → Add modules if Hub offers it, otherwise install them separately and point **Preferences → External Tools** at them.
- **No physical test device yet** (no Android phone, no iPhone/Mac). Test in the Editor with the **Device Simulator** (mid-range Android profile, touch input). On-device performance checks are deferred until an Android phone is bought; keep things mobile-friendly anyway (URP mobile quality tier, low draw calls). Keep code platform-neutral so iOS stays possible later.
- Main scene: `Assets/Scenes/OakValley.unity` (build index 0), the offline hunting zone laid out per design.md's **Oak Valley layout**: a 340×460 m Unity terrain (walkable valley ~240×415 m, ringed by mountains), the Han at the south gate (respawn point), monster spawners by area (see **Monsters** under **Oak Valley layout**), the shepherd, Drangue Leap ledges (glowing cyan rims), HUD. See **Oak Valley layout** below.
- `Assets/Scenes/SampleScene.unity` keeps the M0 smoke test: `Assets/Scripts/Net/NakamaLoginTest.cs` on the `NakamaLoginTest` GameObject device-authenticates against `127.0.0.1:7350` on Play and logs `[Nakama] Logged in as …`. Start the server first. `M0_Cube` there is the M0 MCP test object; delete it freely.
- The Editor's active quality level is **Mobile** (same tier Android uses) in Edit mode, but with the Standalone build target Play mode can fall back to **PC** (see **Oak Valley layout** → phone budget).
- Player settings: landscape only (auto-rotates between the two landscape sides). `ZoneSession` sets `Application.targetFrameRate = 60`.

#### Play-testing Oak Valley (M1)

1. Open `Assets/Scenes/OakValley.unity`, switch the Game view tab to **Simulator** and pick a mid-range Android phone (Unity 6.3 only ships generic profiles: use **Punch Hole Left (1080x2340)**); rotate it to landscape (Screen reads 2340×1080 in Play). Keep a single play-mode view: a second, floating Game view takes over rendering and input when it was focused last. Set by code (editor UI state, saved with the layout): reflect `UnityEditor.DeviceSimulation.SimulatorWindow` (assembly `UnityEditor.DeviceSimulatorModule`) → `m_Main.userInterface`, call `OnDeviceSelected(index)` and set `Rotation = 90`.
2. Press Play. Controls (touch only, the mouse acts as one finger in the Simulator):
   - Touch and drag on the **left ~45%** of the screen: floating joystick (camera-relative).
   - Drag anywhere else: turn the camera.
   - **Tap a wolf** to lock on: you run to it and auto-attack. Or press **Attack** to lock the nearest wolf within 15 m. Moving with the joystick cancels the run-in but keeps the lock.
3. HUD: player HP (top-left), locked target (top-centre), `Slain: N` (top-right). Floating numbers show damage, `N!` crits and `Miss`.
4. Dying shows a 5 s overlay, then you revive at the Han (by the south gate). HP regenerates after 5 s without taking damage. Wolves respawn 10 s after their corpse fades.
5. The Console logs `[Combat] Grey Wolf slain in Oak Valley (N total)` per kill and `[Combat] … defeated / revived` on death. Any red error is a bug.

#### Play-testing skills and Drangue Leap (M2)

- You start as **The Kreshnik** (sword and bow), knowing every book your character can use, with 40 skill points (`dev` block in `skills.json`; books drop as items from M3). Books start at level 0, so open **Skills** (top-right) and spend points first: forms unlock at book levels 1, 3 and 6. Every 5 kills earns a point.
- The skill buttons ring the Attack button and show the current weapon's forms; the subtitle shows the Spirit cost (or the book level that unlocks it), and a dark sweep shows the cooldown. Single-target and Rain of Arrows forms lock the nearest wolf if you have no target and run you into range first; pressing a form while another plays queues it (gold ring). Each cast flashes its exact area on the ground: gold plain, green poison, blue paralysis, violet stun/knockdown.
- **Swap** (top-right) changes weapon: new basic attack (the bow shoots from 13 m) and new skill buttons. The Skills panel's **Play the other character** button switches to The Zana's Chosen (sicas and staff) for testing; it resets skill progress.
- Statuses: Thunder Arrow stuns, Crescent Fan may poison, Spring Wave may paralyse, Wrath of the Zanas may knock down. The target frame lists active statuses, and disabled wolves stop and wobble.
- **Leap** (teal, left of the skill ring) leaps onto the best glowing ledge within 12 m in the joystick direction (or the way you face), within a 100° wedge: try the two stones west of the Han (3 m, then 6 m) and the kulla tower roof, the stones by each meadow pack and the den crag (a safe bow spot), and the ruined tower at the bandit camp (scaffold at ~5 m, then the top at ~9 m). With no marked ledge in reach it's a 6 m ground dash instead; unmarked geometry (the Han, rocks, cliffs) is never a landing spot. `[Leap] Landed on …` is logged per landing.
- Wolves can't bite up onto a ledge (`reachHeight`), so a ledge plus the bow is a safe spot; that's fine offline and gets server rules in M4.
- In the plain Game view the mouse is turned into touches by `TouchSimulation` (Editor only); the Input System skips that while the Device Simulator is open, so there's no double input.

#### Play-testing loot and inventory (M3)

- The Kreshnik starts with the Worn Sword (14–22) worn, the Worn Bow, 5 Healing Draughts, 3 Zana's Dew and 100 gold (`starterKits` in `items.json`); The Zana's Chosen gets the same with sicas and staff. Gold shows under the HP frame.
- Kill wolves: each rolls the `wolf` loot table and its drops pop out around the corpse. Gold is a small coin pile on a gold glow disc; items show their model if `ItemModels.asset` has one (the Iron Sword stands blade-down in the ground), else a spinning pouch, with a beam and disc in the rarity colour (white Common, green Fine, blue Rare). Walk within 3 m (`loot.autoLootRadius`) and it's picked up after 0.4 s: it flies to you and floats `+7 gold` / the item name. Drops vanish after 60 s. With a full bag the drop stays and `Your bag is full` shows once; it's picked up when a slot frees.
- **Bag** (top-right, left of Skills): 30 slots (item icon on a tile shaded by kind, border = rarity, count top-right, short name underneath), the 6 worn slots, and a stats summary (damage range, accuracy, crit, defense, dodge, HP, Spirit, skill damage/defense, poison/paralysis resistance). Tap an item for its card: icon, requirements (red if this character can't use it), stats and bonus lines, green/red changes against what you wear in that slot, and Move + Equip / Unequip / Use. The weapon slot can't be emptied: equip another weapon or press **Swap**, whose label names the weapon it would pick.
- **Moving items**: tap an item, press **Move** on its card (the slot gets a cyan mark, the title says `tap a slot to move … there`), then tap the destination bag slot: an empty slot moves it, the same potion merges the stacks (as much as fits), anything else swaps places. Tapping the item itself, a worn slot, the panel background or the dimmed area outside, **Cancel**, or closing the bag cancels. Tap-based on purpose: no drag handling, so the joystick/camera never see it (the backdrop makes every touch a UI touch). Moves go through `Inventory.Move` (no ledger entry, ownership doesn't change).
- **Panels** (Bag, Shop, Skills) are opaque; while one is open a dark `PanelBackdrop` dims and blocks every HUD control except the player and gold frames, and `PanelFit` places the panel right of those frames or below them (whichever fits larger at that aspect, scaled down only if needed), so they're never covered. Tapping the backdrop cancels a bag move, else closes the panel (the bag in a shop session returns to the shop). Notices move to the top edge while a panel is open.
- Equipping the Iron Sword (21–31, +2% accuracy) puts its model in the Kreshnik's right hand and the next basic attacks roll 21–31 minus the wolf's defense (crits ×1.6).
- **Potion buttons** (left of Leap; slot 1 is the one next to Leap): the potion's icon, name, count left and a cooldown sweep, in the potion's colour; dimmed at 0. Potions are also usable from the bag. **Choosing quick slots**: a potion's card shows **Set slot 1** / **Set slot 2** (outside a shop session); the slot it's already on reads **On slot N**. Putting a potion on the slot the other one holds swaps them (`PlayerItems.AssignQuickSlot`), and the buttons update at once. `inventory.quickSlots` in `items.json` is the starting state (and what a character reset restores).
- **Han Keeper** (greybox NPC by the Han's door, name floating over him): tap him to run over and open his shop (or open at once within 3.5 m). Buy ×1 or ×5 (potions); prices turn red when you can't afford one, and a blocked buy shows the reason. **Sell items from your bag** opens the bag in sell mode (Sell / Sell all on the card; worn gear can't be sold); closing the bag returns to the shop. Walking 7 m away, dying or opening Skills ends the session.
- Console: `[Loot] Grey Wolf dropped 7 gold, Iron Sword (Fine) #local-16` per kill, and a ledger line per change: `[Gold] +7 (loot: Grey Wolf) → 107`, `[Loot] +1 Iron Sword [Fine] #local-16 (loot: Grey Wolf)`, `[Gold] -10 (shop buy: Han Keeper) → 97`, `[Loot] -1 Padded Vest [Common] #local-9 (shop sell)`, plus `[Items] The Kreshnik wields …: basic attack 21–31, …` on every weapon change and `[Shop] Trading with Han Keeper`.
- Wiring: `Gameplay/GroundLoot` (`GroundLoot`: rolls on `ZoneSession.MonsterSlain`, pools `LootDrop.prefab` views and item models, auto-loots with a flat distance check per drop, no physics per frame), `Gameplay/HanKeeper` (`Shopkeeper`, shop id `han_keeper`), HUD `SafeArea/InventoryPanel`, `ShopPanel`, `PotionBar`, `GoldFrame`, `BagButton`, `PanelBackdrop` (drawn above the HUD controls, below `PlayerFrame`/`GoldFrame` and the panels), and `NpcLabels` (`WorldLabel`). `Notice` is the last child of SafeArea so notices draw above panels. Panels rebuild only when `PlayerItems.Version`, the stats or the shop session change.
- **Item icons**: one atlas, `Assets/Items/Icons/ItemIcons.png` (512×512, 128 px per icon, transparent, compressed, no mipmaps), with each icon's UV rect stored in `ItemModels.asset` under the item's `modelKey` (else its id), plus `Gold` and `Pouch`. UI shows them through `RawImage`s (`ItemIcons.Apply`), so the whole bag batches on one texture. Regenerate after adding an item or model: **Wuxia → Items → Generate Item Icons**, or through MCP `execute_code`: `return Wuxia.EditorTools.ItemIconGenerator.Generate();` (`Assets/Scripts/Editor/`, editor-only assembly `Wuxia.Editor`). It renders in a preview scene: registry prefabs as they are (weapons laid on the diagonal, everything else at a 3/4 angle), worn weapons from the Player prefab's greybox weapon of their type, and greybox stand-ins built from primitives for the rest (a bottle in the potion's colour, hood, vest, boots, ring, amulet), with a dark rim so they read on any tile. An item without an icon shows the pouch icon.
- **Item models**: `Assets/Items/ItemModels.asset` (`ItemModelRegistry`) maps an item's `modelKey` to a prefab, used both in hand (`PlayerAppearance` instantiates it once under `WeaponPivot` and hides the greybox weapon) and on the ground (with a per-entry ground offset/rotation, spin and bob). It also holds the gold-pile and pouch prefabs. Items without an entry keep the greybox weapon of their type in hand and drop as a pouch. To add one: import the `.glb` (glTFast; check its `.meta` says `ScriptedImporter`) with its textures split out and compressed (see **Model textures** below; 512 max for items), make a prefab whose **root is the grip** with the model as a child turned so the blade/shaft runs along **+Z** with the flat side facing ±Y (like the greybox sword; for a glb with the blade along +Y that's a child rotation of (90, 0, 0)), no colliders, then add `{modelKey, prefab, groundOffset, groundEuler}` to `ItemModels.asset`. The swing in `CombatVisuals` rotates `WeaponPivot`, so new models swing with it.
- **Bows are the exception** to the +Z rule: the fist's axis points forward, so a bow along it would stick out level. `WornBow.prefab` keeps the model child at identity (glb axes: limbs along +Y, back of the bow +Z, string −Z, grip at the origin) and puts its **hand pose on the prefab root** (local position/rotation under `WeaponPivot`, fitted to the Kreshnik's idle: upright at his side, grip in the fingers). `PlayerAppearance` instantiates with the root's local pose, while the icon generator and `GroundLoot` reset the root, so icons and ground drops see the bow's natural axes (ground: `groundEuler` (0, 30, 8) stands it on its lower tip).

#### Playing online (M4)

- **The Oak Valley scene plays online by default**: the `Net` object's `NetZone` (`Assets/Scripts/Net/`) logs in with the device id, creates the character the Player is set to (`PlayerCombat.characterId`, named after it) if the account doesn't have it, asks `zone_join` for an `oak_valley` channel and joins it. Start the dev server first (`docker compose -f server/docker-compose.yml up -d --build`). Console: `[Net] Logged in …`, `[Net] Joined Oak Valley channel 1 as The Kreshnik (kreshnik): N other player(s), 30 monsters`, and a notice `Online · Oak Valley channel 1`. No server within `connectTimeout` (10 s): `[Net] Playing offline: …` and the zone plays exactly as in M1–M3 (local spawners, rules and loot). Untick `NetZone.connectOnStart` to always play offline. The protocol is `server/PROTOCOL.md`.
- **What changes online**: the server runs the monsters (the scene's monster prefabs in `MonsterAI` remote mode: placed and moved from snapshots, `SpawnRemote`/`SetRemoteState`/`DespawnRemote`, no local AI or NavMeshAgent), decides every hit (`Combatant.ReceiveHit` from `hit` events; HP from snapshots with `SetHp`; deaths with `Kill`), auto-attacks the locked target (`PlayerCombat.Engage` sends `Target`), resolves skill forms (`PlayerSkills` plays the cast and its effect at once and sends `Cast`), checks leaps (`DrangueLeap` sends `Leap` with the ledge's name), regenerates HP and Spirit, revives you at the Han, drops loot for whoever dealt the most damage and auto-loots it (`GroundLoot.SpawnNet`/`RemoveNet`), and owns gold, items, skills and kills (`Self` → `PlayerItems.ApplyServerState`, `PlayerSkills.ApplyServerSkills`, `ZoneSession.SetKills`). Item, shop, potion and book actions go through `PlayerCombat` (`Equip`, `Unequip`, `SwapWeapon`, `UseQuickSlot`, `UseItem`, `Buy`, `Sell`, `MoveItem`, `AssignQuickSlot`) and `PlayerSkills.LevelUpBook`, which send an `Action` when `NetZone.Online`; a refusal shows the server's wording as a notice. Movement stays local: 10 position updates a second, and a refused one comes back as a correction (`[Net] Move corrected (…)`). The Skills panel's **Play the other character** leaves the channel and rejoins as that character (created on first use), with its own saved progress.
- **Other players** are their character model (`Kreshnik.prefab`/`ZanasChosen.prefab`) with a `RemotePlayer` (slides to each snapshot, runs by speed, lies down when dead) and a name label copied from the HUD's `NpcLabels/HanKeeperName`. They don't show their weapon or attack animations yet; their hits show on the monsters.
- **A second player without a second device**: `node server/tests/bot.mjs --url http://127.0.0.1:7350 --seconds 90` logs in as another device (`--device`, `--character zanas_chosen`, `--name "Bora Bot"`), joins the same channel, follows the first other player and fights whatever monster is next to them, printing every hit and kill. A second account from the same machine in a build: command line `-wuxiaDevice <suffix>` (or `NetZone.deviceIdSuffix`).
- **Driving it through MCP**: Play mode stalls while the Editor isn't focused; for an online session set `Application.runInBackground = true` from `execute_code` right after entering Play (runtime only; the player setting stays off), or the connect times out on wall-clock time and the zone goes offline.
- Verified in the Editor with the bot: both hit the same wolf, the kill went to the bigger damage dealer on both sides, loot auto-looted (`gold 100 → 106`), skill point spent and Eagle Strike landed (39 damage), potion drunk (HP 116 → 192, 8 s cooldown), leap onto LeapStone Meadow West accepted by the server, character switch, rejoin at the saved spot with saved kills, and the offline fallback.

#### Oak Valley layout

- South to north (z grows north, the Han is at about (-16, -192)): south gate (closed, `To Dardana` sign) and the Han; meadow Lv 1–4 (both meadow packs, the **Old Shepherd** with his hut, pen and sheep); oak forest Lv 5–8 with the **dried spring** in a clearing west of the road; the river, crossed only by the **stone bridge** (invisible `River Walls` on both banks; the NavMesh is cut the same way); upper valley Lv 8–12 with the **bandit camp** on a hill against the west slopes (ruined tower, palisade open to the east, tents, campfire with a point light) and the **wolf den** (`WolfDenPack`, cave mouth) under the east slopes; the **north pass** to Serpent Marsh (standing stones, signpost, closed for now). Han to north pass is ~390 m of road, ~70 s at run speed.
- **Areas**: `Gameplay/Areas` holds one `ZoneArea` per part (name, level band, ground-plane box, priority on overlap). `ZoneSession` checks the player's area every 0.25 s and raises `AreaChanged`; the HUD's top-right reads `Oak Valley · Oak Forest  Lv 5–8` and entering flashes `Oak Forest · Lv 5–8` (2.5 s). `[Zone] Entered … (Lv …)` is logged. The level bands are layout data in the scene for now (no monsters read them yet).
- **Monsters** (stats in combat.json, loot tables in items.json, one `MonsterSpawner` each under `Gameplay`): meadow, Grey Wolves Lv 2 (`MeadowWestPack`, `MeadowEastPack`, 5 each); oak forest, **Wild Boars** Lv 6 (`BoarSpringHerd` in the dried spring's clearing, `BoarEastHerd` in a clearing east of the road, 4 each; they aggro at 5 m and hit hard and slowly); bandit camp, **Bandits** Lv 9 (`BanditCampGang`, 5 inside the palisade, and `BanditLookouts`, 3 at the east opening; they aggro at 8 m and call each other in from 12 m); wolf den, **Den Wolves** Lv 11 (`WolfDenPack`, 4). The player is level 1 until M7, so the camp and above all the den are meant to be beyond a fresh character: a level-1 Kreshnik in Worn gear dies to the den pack in ~10 s (the den crag ledge plus the bow still works). The level bands on the areas are still layout data only (nothing reads them).
- **Monster prefabs** share one setup (`Wolf.prefab` is the template): root on `Monster` with `NavMeshAgent`, `CapsuleCollider`, `Combatant` (`aimHeight` = where floating numbers start), `CombatVisuals`, `MonsterAI` (`monsterId` picks the combat.json entry; `packAssistRadius`, `personalSpace`) and `MonsterAnimator`, with `Visual/Model` holding the `.glb` instance and its Animator. Each species has a copy of `Wolf.controller` (same `Gait`/`Playback`/`Attack`/`Dead` parameters: idle/walk/run blend, attack and death) with its own clips; attack and death are non-looping `.anim` copies of the glb clips (`<Name>_Attack.anim`, `<Name>_Death.anim`), since glTFast imports every clip looping. `MonsterAnimator.walkClipSpeed`/`gallopClipSpeed` are the ground speeds the walk/run clips match at the prefab's scale (measured in Blender from planted-foot slide; boar 0.35 / 1.85 m/s with `maxPlayback` 3, bandit 1.1 / 2.4). glTFast models already carry an `Animator`; reuse it rather than adding one.

The originals stay in the scene with their colliders and keep editing simple; keep scattered objects off Batching Static. - **Atmosphere (sun, sky, fog, post)**: each area gets the mood of its key art in `docs/art/oak-valley/`: **Afternoon** (the Han, the meadow, the shepherd's fold: warm sun at 28°, blue sky, pale haze), **Forest** (oak forest and dried spring: low gold sun, amber haze), **Sunset** (upper valley), **Dusk** (bandit camp: blue hour, the campfire carries the scene), **Overcast** (wolf den: grey, desaturated) and **MarshMist** (road to Serpent Marsh: green mist). Each mood is an `AtmosphereProfile` asset in `Assets/Art/OakValley/Atmosphere/` (`<Mood>.asset`: sun elevation/azimuth/colour/intensity/shadow strength, trilight ambient, linear fog, sky colours, cloud cover, fade time) with its colour grading in `<Mood>_Post.asset` (colour adjustments, white balance, split toning). `Base_Post.asset` holds what every mood shares: Neutral tonemapping, bloom (dual filter, quarter resolution, 4 iterations, threshold 1, mobile-cheap) and a light vignette. **Tune the assets** (inspector or MCP); nothing in code holds those numbers. `Generated/Atmosphere` (built by `OakValleyBuilder.SetUpLighting`; the area-to-mood table is `Moods` there) has `ZoneAtmosphere`, the `Base` volume and one volume per mood. Moods only differ in light, colour and fog, so a phone pays the same in every area. Main Camera has post-processing on. To compare with the key art: **Wuxia → World → Capture Atmosphere Shots** (MCP: `return Wuxia.EditorTools.AtmosphereShots.Capture("tag");`, optional spot names) renders the game camera's view at fixed spots per area (Edit mode, Mobile tier, post on, no occluder fade) to `Temp/Screenshots/<tag>-<spot>.jpg`. Measured in the Editor (Mobile pipeline, GPU recorders): opaques 0.48 ms, bloom 0.10 ms, uber post 0.10 ms, LUT 0.02 ms; post adds ~17 set-pass calls and ~0.25 ms main-thread CPU. If a phone can't hold 60 fps, turn off Bloom in `Base_Post.asset` first (it's half the post cost).
- **Occluder fade**: scatter is merged per cell, so crowns in front of the camera are cleared per pixel, not per tree. `Foliage.mat` uses **`Wuxia/Foliage`** (`Assets/Art/Shaders/`), which is URP Lit's own forward, shadow and meta code plus a dither clip (`OccluderFade.hlsl`): fragments inside a capsule from the camera to the player's chest, or right by the lens, are discarded through a 4×4 screen-space Bayer pattern. It stays opaque (no blending or sorting, same batches, SRP Batcher compatible). With the fade off, renders are pixel-identical to URP Lit. The colour, DepthOnly and DepthNormals passes clip the same fragments. ShadowCaster doesn't, so canopy shadows stay put. `CameraOccluderFade` on the Main Camera (runs after `ThirdPersonCamera`) sets the capsule as shader globals each frame. It turns the global keyword `_OCCLUDER_FADE` on only while a collider on `occluders` (Obstacle: trunks, rocks) is within `radius + crownMargin` of that line, because clipping shaders lose early-depth/hidden-surface optimisations on phone GPUs. So the meadow and the Han views draw without a clip, and the forest has it on nearly all the time. The strength eases in and out over `fadeInTime`/`fadeOutTime`. Tune it on that component: `radius` (2 m) and `edgeSoftness` (dithered rim, 0.5 m), `endSoftness` (eases out before the chest so scatter beside and behind the player stays), `nearRadius`/`nearSoftness` (cleared around the lens), `maxFade` (1 = fully cleared), `chestHeight`, `crownMargin` (8 m, about the widest crown's radius). The Bayer pattern is in the shader. `OakValleyBuilder` gives `Foliage.mat` the `Wuxia/Foliage` shader, so a rebuild keeps it. The depth passes assume no normal/parallax/detail/alpha-clip maps (Foliage.mat uses none).

#### Game data and tests

- Combat numbers (player and monster HP, Spirit, resistances, characters and their weapons' basic attacks, accuracy, dodge, crit, ranges, speeds, aggro/leash, respawn timers) live in **`shared/gamedata/combat.json`**. Skill books, forms (shape, range, radius, cone angle, Spirit, cooldown, cast time, damage, status), statuses, skill-point costs and Drangue Leap limits live in **`shared/gamedata/skills.json`**. Items (gear, weapons, potions with their stats, prices, level requirement, allowed characters, `modelKey`), rarities and their bonus-line pool, bag capacity and potion quick slots, starter kits, NPC shops, loot tables (per monster), auto-loot radius and ground time, stat caps, and the offline player level (`offline.playerLevel`, 1 until M7) live in **`shared/gamedata/items.json`**. Zone layouts the server runs (respawn point, shopkeepers, leap ledges, monster packs, areas) and the server-side tuning (tick rate, saves, move checks, and the monster AI and player values the client keeps as serialized fields today) live in **`shared/gamedata/zones.json`**; Oak Valley's spots are copied from `OakValley.unity`, so update them when `OakValleyBuilder` moves a pack, ledge or the Han. `ZoneSession` loads the first three through TextAsset references to `Packages/com.wuxia.gamedata/…` (new JSON files there get a `.meta` from Unity; commit it). Edit the JSON and re-enter Play; no code change needed. Field names are mirrored in `Assets/Scripts/Data/CombatData.cs`, `SkillData.cs` and `ItemData.cs`; keep them in sync. The wolf table drops the Iron Sword at 2%; to see one quickly while testing, raise its `chance` locally and don't commit it.
- Rules that move to the server in M4 are pure C# (no Unity types, `System.Numerics` vectors) in `Wuxia.Combat`:
  - `CombatMath`: basic attacks. Hit chance = accuracy − dodge, clamped to 5–99%; damage = roll(min..max) × crit multiplier − defense, at least 1.
  - `SkillShapes`: which targets a form hits. Single = the locked target in range; cone = within `range` and `angle`/2 of the facing (towards the locked target, else forward); circle = within `radius` of the caster; circleAtTarget = within `radius` of a locked target that is within `range`. Measured on the ground plane to target centres, edges inclusive, and targets beyond the weapon's `reachHeight` above/below are skipped.
  - `SkillMath`: forms always hit and never crit; damage = roll(min..max) × (1 + `damagePerBookLevel` × (book level − 1)) × (1 + caster's skill damage) − (defense + skill defense), at least 1. Status chance = chance × (1 − resistance).
  - `SkillState`: learned books and levels, skill points and the kill meter, Spirit, cooldowns. `StatusSet`: statuses refresh rather than stack; poison ticks every `tickInterval`.
  - `LeapRules`: a landing must be a marked ledge, within `maxDistance` on the ground plane and within `maxRise`/`maxDrop`. `World.LeapPlanner` (Unity side) finds the ledge and checks its top is clear with a downward raycast.
- Items and gold are pure C# in `Wuxia.Items` (`Assets/Scripts/Items/`), same server-bound rule:
  - `PlayerItems` is the **one place gold and items change** (wallet, bag, 6 gear slots, quick slots, potion cooldowns). Every change raises `Ledger` (`[Gold]`/`[Loot]` lines in the Console; a server ledger row from M4); every item instance has a unique id from `ItemFactory`. At runtime it's `PlayerCombat.Items`; `PlayerCombat.Stats` holds the computed stats.
  - `StatCalculator`: combat.json base + everything worn (bonus lines included). The weapon item's damage *replaces* its weapon type's basic-attack damage (range, interval, crit stay per type in combat.json; the Worn weapons match the old combat.json numbers); other gear adds. Dodge and poison/paralysis resistance are capped by `statCaps`. Gear changes re-apply stats to the `Combatant` and max Spirit to `SkillState`.
  - Rules: equipping swaps the old item into the same bag slot; weapons are locked to characters and their weapon types; level requirements are real (vs `offline.playerLevel`); the weapon slot can't be emptied; unequip fails on a full bag. Swap wields the other weapon type from the bag (last used, else highest average damage). Adding to the bag is all-or-nothing (potions top up stacks first), so a drop that doesn't fit stays on the ground. Shop buy is atomic (gold and bag both change or neither); worn items can't be sold; sell price × rarity `sellMultiplier`. Potions restore up to max, can't be drunk dead or at full, and share a cooldown per `cooldownGroup`. Switching character resets to that character's starter kit (state is in-memory until M4).
  - `LootRoller` rolls a monster's table (gold, then each entry independently); gear drops roll a rarity by `dropWeight` and that many distinct bonus lines for their slot. `ZoneSession.MonsterSlain` fires per player kill.
- EditMode tests: **Window → General → Test Runner → EditMode → Run All**, or through MCP `run_tests` (mode EditMode, assembly `Wuxia.Tests.EditMode`). They cover `CombatMath`, skill shapes (every form in `skills.json` is checked just inside and just outside its edges), book progression, Spirit and cooldowns, statuses, the leap rules and the ledge search (real colliders built at x/z 5000 and destroyed after each test), equipment and the stat calculator (the Iron Sword raises the basic attack), bag capacity and stacking, shop atomicity, potions and quick-slot assignment, bag moves, the ledger, loot odds with a seeded RNG, and sanity-check all three JSON files (every referenced item exists, weapon types match combat.json).

### Unity MCP bridge (Claude Code ↔ Unity Editor)

- Package: MCP for Unity (CoplayDev, `com.coplaydev.unity-mcp`, pinned in `client/Packages/manifest.json`). Its Python server runs through `uvx` (needs `uv` installed).
- Transport: HTTP at `http://127.0.0.1:8080/mcp`, registered in `.mcp.json` as `UnityMCP`.
- To connect: open `client/` in Unity — the package auto-starts the server (EditorPref `MCPForUnity.AutoStartOnLoad`, set on this machine; on a new machine tick auto-start in **Window → MCP for Unity** or click **Start Server**). Then start Claude Code from the repo root. Check with `/mcp`.
- Ready signals: Unity Console shows `MCP-FOR-UNITY: Session connected`; `curl http://127.0.0.1:8080/mcp` answers (406 is fine). The bridge only exists while the Editor is open.
- On each Editor start the package also writes a matching local-scope `UnityMCP` entry for this repo into `~/.claude.json`. That's expected and harmless (same URL).
- Don't use the Unity window's **Configure** button for Claude Code: it removes `UnityMCP` from every scope (including this repo's `.mcp.json`) and re-adds it at local scope.
- Per the design doc, scenes and prefabs are wired **through MCP**, not by hand-editing `.unity`/`.prefab` YAML. Bulk greybox work (scatter, prefab meshes, HUD layout) is easiest with `execute_code` (in-editor C#; its compiler is C# 6 with no `using UnityEngine.UI`, so fully qualify UI types and write `UnityEngine.Object`).
- MCP screenshots default to `Assets/Screenshots`; pass `output_folder: "Temp/Screenshots"` so they don't land in the project. A capture without a `camera` can show a cyan world when the Game view isn't focused; pass `camera: "Main Camera"` (that leaves out the overlay HUD). `manage_camera screenshot` (re)opens a small floating portrait **Game view** (482×797) that then becomes the main play-mode view instead of the Simulator; close it afterwards (`GameView` windows that aren't `docked` → `Close()`), or capture by rendering `Camera.main` (or a temporary camera) into a RenderTexture from `execute_code` and writing a PNG to `Temp/Screenshots`.

The server package (`uvx mcp-for-blender`) and the addon must share a protocol version (`ADDON_PROTOCOL_VERSION` in `addon.py`); `uvx --refresh mcp-for-blender` picks up a new server.
- Models made in Blender still follow **Model textures** and the item-prefab rules above: export `.glb` with images split out, compressed in Unity, originals in `art-source/`.
- **`art-source/GameAssets.blend`** is the working file: one collection per game model (Kreshnik, ZanasChosen, Wolf at its native size (`Wolf.prefab` scales it ×0.4), the game's IronSword, WornBow). Blender Z-up maps to Unity +Y and Blender −Y to Unity +Z, so model a weapon with its grip at the world origin. `WornBow_Parts` (hidden) holds the bow's separate, editable parts with their procedural materials (wood grain, leather, red wool cord, horn, linen); `WornBow` is them joined, UV-unwrapped, and baked (Cycles, Diffuse colour only) into one 512 px `WornBow_BaseColor`. To change the bow, edit the parts, re-join, re-bake, and export only `WornBow` (deselect everything first: objects in hidden collections stay selected and get exported too).

## Conventions

- **Server-authoritative.** Anything that affects gold, items or combat outcomes is decided on the server; the client only predicts visuals. Upgrade rolls, trades and market actions are single atomic server calls, and every gold/item change is logged.
- **Shared game data** (skills, items, monsters, drop tables, odds) lives in one set of JSON files under `shared/gamedata/`, loaded by both client and server, so numbers never drift. Never hard-code a balance number in C# or TypeScript.
- **Git LFS** tracks binary assets (textures, models, audio, fonts, native libs) — see `.gitattributes`. Run `git lfs install` once per clone. Unity always saves terrain data and baked NavMeshes in binary, whatever the serialization mode, so `.gitattributes` sends `NavMesh-*.asset` and `*Terrain.asset` to LFS too: as text, `eol=lf` stripped CR bytes out of them and Unity could no longer load them. Any new binary `.asset` needs the same. Never commit `client/Library/`, `Temp/`, `Logs/`, `UserSettings/` or builds.
- Unity: keep `.meta` files with their assets; C# under `Assets/Scripts/`, namespace `Wuxia.<Area>`.
